# Аудит сервиса «Для мам» перед массовым запуском

*Дата: февраль 2026*

---

## 1. Безопасность

### 1.1. Аутентификация и авторизация
- **JWT**: используется для защиты API, срок жизни 7 дней. Рекомендация: для массового запуска рассмотреть сокращение до 1–3 дней или refresh-токены.
- **Telegram initData**: проверка подписи через `verifyTelegramInitData` (HMAC) — корректно, подделка сессии без бота невозможна.
- **Guards**: все эндпоинты с персональными данными защищены `JwtAuthGuard` — доступ только авторизованным пользователям.
- **Права доступа**: удаление заявок/объявлений — только автор или админ (username `tigrbn`). Логика проверки владельца и админа реализована.

**Рекомендации:**
- Убедиться, что файл `.env` (с `DATABASE_URL`, `JWT_SECRET`, `BOT_TOKEN`) **никогда не попадает в репозиторий** (проверить, что он в `.gitignore` и не был закоммичен ранее).
- Использовать **сильный JWT_SECRET** (минимум 32 случайных байта, не словарь). На проде хранить секреты в отдельном файле (например `api.env` вне репозитория) и не логировать их.

### 1.2. CORS и заголовки
- **CORS**: `enableCors({ origin: true })` — разрешён любой origin. Для Mini App в Telegram это допустимо (запросы идут с домена Telegram). При желании можно ограничить origin списком доменов фронта.
- **Helmet**: не используется — нет дополнительных security-заголовков (X-Content-Type-Options, X-Frame-Options и т.д.). Рекомендация: подключить `helmet` в `main.ts` для снижения рисков XSS/clickjacking.

### 1.3. Загрузка файлов
- Лимит размера: **5 MB** на файл (multer).
- Типы: только `image/jpeg`, `image/png`, `image/gif`, `image/webp` (проверка по `mimetype`).
- Имя файла на диске: `randomUUID() + ext` — предсказуемых имён нет, path traversal через имя отключён.
- Каталог `uploads` создаётся при старте, раздача только по префиксу `/uploads/`.

**Рекомендации:**
- В nginx для API уже рекомендуется `client_max_body_size 10M` (см. NGINX.md) — убедиться, что это применено, иначе загрузка больших фото вернёт 413.

### 1.4. Валидация входящих данных
- **Заявки**: категория и описание обязательны, описание не короче 10 символов. Максимальная длина текста не ограничена — теоретически возможна очень длинная строка (PostgreSQL `text` выдержит, но стоит ввести лимит, например 2000–5000 символов).
- **Объявления (posts)**: контент не короче 10 символов, до 10 изображений. Максимальная длина контента не ограничена — рекомендация: лимит 3000–5000 символов.
- **imageUrls в POST /posts**: принимаются любые строки. Сейчас URL формирует только наш `/upload` (путь вида `/uploads/...`). Рекомендация: на API проверять, что каждый URL начинается с `/uploads/` (или с доверенного домена), чтобы не сохранять ссылки на сторонние ресурсы.
- **Отклики**: комментарий не короче 10 символов.
- **Профили**: проверки на обязательные поля и типы есть в сервисах; глобального ValidationPipe нет — валидация разбросана по контроллерам/сервисам.

### 1.5. SQL-инъекции и Prisma
- Запросы к БД через **Prisma** — параметризованные запросы, риска SQL-инъекций при обычном использовании нет. Raw-запросы в `me.controller` используют `Prisma.sql` и привязку параметров — безопасно.

## 2. Надёжность и ограничения

### 2.1. Лимиты выборок
- Лента: баннеры — 5, посты «Другое» — 20, заявки — 50, специалисты — до 100 с последующим slice(0, 50).
- «Мои заявки» / посты: до 50 записей.
- Пагинация на фронте (ITEMS_PER_PAGE) — переключение страниц без перезапроса всего списка с бэкенда; бэкенд отдаёт весь список. Для очень активных пользователей можно добавить пагинацию на API (limit/offset или cursor).

### 2.2. Уведомления в Telegram
- При создании заявки вызывается `notifySpecialistsAboutNewRequest` — рассылка специалистам с подпиской на категорию. Вызов не блокирует ответ пользователю (`void`). При сбое Telegram API ошибка логируется в TelegramService; повтор при неудаче не реализован — рекомендация: при росте нагрузки рассмотреть очередь с повторами.

### 2.3. Ошибки и логирование
- NestJS возвращает стандартные HTTP-коды и сообщения (400, 401, 403, 404). Глобального exception filter или единого формата ошибок для клиента нет — фронт ориентируется на статус и текст.
- Логи: используется встроенный Logger в части сервисов (Auth, Profiles). Рекомендация: настроить единый логгер (например, в файл/сервис) и не логировать персональные данные и токены.

### 2.4. Health check
- Есть эндпоинты `/health` и `/health/db` (проверка соединения с БД). Удобно для мониторинга и балансировщиков.

## 3. Юридическая и пользовательская часть

- **Пользовательское соглашение**: в приложении есть страница документа с разделом 8 «Пользовательский контент» (в т.ч. право оператора на хранение и отображение контента).
- **Политика обработки персональных данных**: есть раздел 2.3 «Изображения и мультимедийные материалы».
- **Согласие**: при первом входе/создании профиля запрашивается принятие соглашения и политики, факт фиксируется в БД (consentLog).
- **Дисклеймеры в интерфейсе**: под загрузкой фото — текст про права и ответственность; в карточке специалиста — про то, что материалы размещены пользователем и сервис не проверяет достоверность и законность.

Перед запуском стоит ещё раз проверить актуальность текстов с юристом.

## 4. Инфраструктура и деплой

- **Обновление на сервере**: в NGINX.md описаны шаги (git pull, npm ci, prisma generate, migrate deploy, build API и фронта, pm2 restart). Важно не забывать `npx prisma migrate deploy` при появлении новых миграций.
- **Переменные окружения**: на проде должны быть заданы `DATABASE_URL`, `JWT_SECRET`, `BOT_TOKEN` (и при необходимости `TELEGRAM_DEV_CHAT_ID`). Для запуска в мессенджере MAX дополнительно задают `MAX_BOT_TOKEN` (см. `docs/MAX_SETUP.md`). Файл с секретами лучше хранить вне репозитория (как в примере с `api.env` в NGINX.md).
- **Резервное копирование БД**: в документации не описано. Рекомендация: настроить регулярные бэкапы PostgreSQL (cron + pg_dump или средства хостинга).
- **SSL**: запросы к приложению должны идти по HTTPS (настройка на стороне nginx/провайдера).

## 5. Рекомендации по приоритетам перед запуском

### Критично
1. **Секреты**: убедиться, что `.env` не в репозитории; на проде использовать отдельный файл с сильным JWT_SECRET. *(Пользователь обновил .env на сервере.)*
2. **Nginx**: проверить `client_max_body_size 10M` для location API, иначе загрузка фото может не работать.
3. **Резервное копирование БД**: настроить регулярные бэкапы.

### Желательно (реализовано в коде)
4. **Лимиты длины текста**: введены — описание заявки до 2000 символов, контент объявления до 3000 символов.
5. **Валидация imageUrls**: при создании поста принимаются только URL, содержащие `/uploads/`, без `..`, длиной до 500 символов.
6. **Helmet**: подключён в `api/src/main.ts` — добавлены security-заголовки.

### По мере роста
7. **Rate limiting**: ограничение числа запросов с одного пользователя/IP (например на auth, создание заявок, загрузку файлов).
8. **Пагинация на API**: для списков «мои заявки» / «мои объявления» при большом числе записей.
9. **Мониторинг**: логирование ошибок и метрик (доступность, время ответа, ошибки 5xx).
